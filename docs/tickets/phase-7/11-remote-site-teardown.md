## What to build

**显式的远端站点下线**：把远端站点真正撤下，与「在后台停用一份站点配置」是两件不同的事。

本 Ticket 的存在理由：作者已明确要求停用与下线是**两个动作**（停用=仅后台隐藏、线上保持不动；下线=移除远端部署并回收）。此前它在 P7-03（只负责停用文案区分）与 P7-09（明写「不在本 Ticket」）之间被互相推掉，没有任何一张票拥有它。**一个已决定要做的行为不得悬空**——本仓库这条线此前反复失败的方式之一就是留下没有归属的延后项。

## Acceptance criteria

- [ ] 后台提供**独立的「下线远端站点」动作**，与「停用配置」在入口、措辞与确认流程上完全不同，不可互相替代。
- [ ] **二次确认**：确认框明确写出将要发生什么（远端部署将被移除、读者将无法访问该地址），并明确写出**不可逆**。
- [ ] 下线后：远端地址不再服务该站点；CMS 侧交付记录保留且标记为已下线；该站点不可再发起交付。
- [ ] **交付记录与历史产物是否保留由实现明确决定并写入文档**；默认倾向保留（下线可逆性差，但记录是审计链）。
- [ ] 幂等：对已下线的站点再次执行下线，明确报出已下线，不产生误导性失败。
- [ ] 远端已不可达时，下线动作**明确失败并保留可重试状态**，不得把「无法确认」报成「已下线」。
- [ ] 下线操作写审计。
- [ ] **不得**通过删除站点配置行来实现下线；停用/删除与下线是三个互不替代的概念。
- [ ] 与 P7-09 的失败语义一致：远端结果不可知时进入待核实，而不是假定成功。
