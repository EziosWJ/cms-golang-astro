# GitHub Blog 内容迁移至生产 CMS

## Problem Statement

博客作者希望把 GitHub `EziosWJ/blog` 的文章与图片迁入已部署的生产 CMS，后续统一在 CMS 编辑和发布。旧博客仍可访问，但迁移期间暂停内容更新。迁移需要保留正文、日期、分类、标签、封面、原文章路径和媒体路径，不能覆盖生产已有内容，也不能误发布源草稿。

现有导入工具已经支持预检和创建工作稿，但没有自动处理外链图片托管、源草稿的发布筛选或站点资料迁移。本地历史盘点的 95 篇文章对应旧提交，不能作为本次迁移数量的验收依据。生产使用 PostgreSQL，不能直接套用默认指向本地 SQLite 的开发导入入口。

## Solution

固定已核实的 GitHub 来源提交，重新盘点文章、公开状态和资源。备份生产数据库、媒体和发布状态后，通过现有受控导入能力创建工作稿、修订和 CMS 媒体；对外链图片及不兼容语法做可追溯转换。冲突内容不自动覆盖，无法修复的内容保留待处理且不发布。

沿用旧站资料和 UTC 日期展示，使用现有 Comic 主题。后台保持原访问入口，博客使用已部署的独立静态服务。导入后先完成数据核对、隔离构建和页面检查，向作者提交迁移报告；只有作者确认报告后，才通过现有发布流程发布验收通过的原公开文章。源草稿及其他未公开内容保留为工作稿。

## User Stories

1. As a 博客作者, I want 固定本次 GitHub 内容提交, so that 预检、导入和验收使用同一份来源。
2. As a 博客作者, I want 重新盘点最新来源中的文章和资源, so that 不把历史调查数量当成当前实际数量。
3. As a 博客作者, I want 区分原公开文章、源草稿和其他未公开内容, so that 迁移不会意外公开私有内容。
4. As a 博客作者, I want 迁移全部原公开文章, so that 新博客能够承接旧博客的内容。
5. As a 博客作者, I want 未公开内容只导入为工作稿, so that 我可以在 CMS 中继续编辑并自行决定发布时间。
6. As a 博客作者, I want 保留文章标题和正文, so that 迁移不会丢失已有创作内容。
7. As a 博客作者, I want 保留展示日期和已有更新时间, so that 导入时间不会改变文章历史。
8. As a 博客作者, I want 保留多分类和标签, so that 原有内容组织方式继续可用。
9. As a 博客作者, I want 保留封面及正文媒体引用, so that 文章信息和阅读效果完整。
10. As a 读者, I want 中文和数字 Slug 对应的旧文章路径继续可用, so that 迁移后仍能找到原文章。
11. As a 读者, I want 原有图片和附件路径得到保留, so that 旧资源引用不会失效。
12. As a 读者, I want 相对文章链接转换后仍指向正确文章, so that 能继续沿正文链接阅读。
13. As a 博客作者, I want 可获取的外链图片迁入 CMS 媒体管理, so that 新站可以自行托管这些图片。
14. As a 博客作者, I want 外链图片原地址与新媒体之间有映射记录, so that 可以核对转换结果并追踪问题。
15. As a 博客作者, I want 图片或附件缺失得到明确报告, so that 不会在未知情况下发布损坏内容。
16. As a 博客作者, I want 无法解析的文章链接得到明确报告, so that 可以在发布前修复阅读路径。
17. As a 博客作者, I want 特殊语法允许转换并逐项记录差异, so that 可以判断转换是否保留了原意。
18. As a 博客作者, I want 无法修复的文章暂缓发布, so that 其余通过验收的文章仍能上线。
19. As a 博客作者, I want 生产已有文章和媒体冲突不被自动覆盖, so that 已有内容得到保护。
20. As a 博客作者, I want 冲突条目单独列出, so that 可以逐项决定如何处理。
21. As a 运维人员, I want 写入前备份生产数据库、媒体及发布状态, so that 迁移出现问题时有恢复依据。
22. As a 运维人员, I want 核对备份可恢复性, so that 备份文件能够实际用于恢复。
23. As a 运维人员, I want 使用生产 PostgreSQL 配置执行导入, so that 不会误写开发数据库。
24. As a 运维人员, I want 导入期间协调写入和发布执行器, so that 不会与其他修改或发布竞争。
25. As a 博客作者, I want 导入先形成工作稿和修订, so that 导入行为不会直接改变读者可见内容。
26. As a 运维人员, I want 稳定来源身份和重复执行不产生重复文章或媒体, so that 部分失败后能安全继续。
27. As a 运维人员, I want 部分成功和失败结果均可追溯, so that 重跑范围和剩余问题清晰。
28. As a 博客作者, I want 沿用旧站站名、副标题、作者和简介, so that 新博客延续已有身份。
29. As a 博客作者, I want 沿用可支持的导航和社交信息, so that 读者仍能找到原有入口。
30. As a 读者, I want 日期继续按 UTC 展示, so that 迁移不会造成日期展示偏移。
31. As a 博客作者, I want 新站使用当前 Comic 主题, so that 能基于已有主题能力完成迁移。
32. As a 博客作者, I want 管理后台与公开博客保持独立入口, so that 管理和阅读职责清晰。
33. As a 博客作者, I want 正式发布前收到数据和页面检查报告, so that 可以决定是否批准上线。
34. As a 读者, I want 表格、代码块、语言标记、标题锚点和图片正常展示, so that 技术文章仍可阅读和使用。
35. As a 博客作者, I want 只有确认过的原公开文章进入发布任务, so that 未公开工作稿不会顺带上线。
36. As a 运维人员, I want 发布失败时继续提供原发布产物, so that 构建故障不会破坏已有站点。
37. As a 博客作者, I want 旧博客迁移期间继续可访问, so that 读者仍能使用原站。
38. As a 博客作者, I want 迁移后在 CMS 统一编辑文章, so that GitHub 内容不成为第二个持续同步的数据源。
39. As a 运维人员, I want 配置、密钥、数据库和附件留在运行环境, so that 公开源码仓库不会包含生产数据。
40. As a 博客作者, I want 报告说明未执行的验收和原因, so that 能区分已验证结果与待验证事项。

## Implementation Decisions

- 复用 Legacy Import、Content、Taxonomy、Media、Site Config、Publishing、Builder 和 Static Web 的既有职责。此任务是实际内容迁移及必要的兼容补齐，不重新实现内容管理系统。
- CMS DB 是内容主数据源；生成 Markdown 仅用于构建；Git 管理源码并提供此次单向迁移来源，不建立双向同步。
- 来源固定为已核实的提交 `eb1cb1671fe353c4ce7bc21e6283e97fb7c1470a`。若执行时需要改用其他提交，须明确变更迁移基线并重新预检，不静默更新来源。
- 盘点同时保存来源文章身份、公开状态、Slug、元数据、媒体引用和转换映射。历史的 95 篇调查仅作参考；实际数量由固定版本的清单确定。
- 现有导入器只扫描 Markdown，不支持 MDX；源草稿标记不会自动成为发布筛选条件。因此须显式识别未公开内容并生成允许发布的清单，不能导入后无条件全量发布。无法判定公开状态的条目不得直接加入发布清单。
- 首选复用受控 CLI 和已有服务契约；预检与正式应用分开。导入使用有相应权限的系统用户，记录审计，不假设特定用户 ID 必然具备权限。
- 生产目标使用已部署的 PostgreSQL 配置和运行目录，禁止照搬默认写入开发 SQLite 的入口。数据库迁移仍显式执行，API 启动不自动迁移。
- 写入前协调暂停 CMS 写入和发布执行器，确认执行器已暂停并释放锁；备份 PostgreSQL、私有媒体、当前站点指针、保留发布产物及恢复所需配置。密钥安全保存，不出现在公开报告中。
- 备份恢复验证在隔离环境进行。明确迁移前状态及恢复步骤，不能只凭备份命令成功宣称可恢复。
- 导入创建工作稿、不可变修订和私有媒体，不自动发布；使用稳定来源身份和指纹支持重复执行。逐条提交发生部分失败时，保留成功条目的证据，不通过清空生产数据重跑。
- 保留正文与元数据；文章链接和媒体引用通过 Markdown AST 转换，避免改写代码示例。每项特殊语法转换记录来源、结果和差异。
- 外链图片使用可追溯的迁移准备步骤下载并接入已有媒体导入能力，保存原地址与 CMS 媒体映射，处理相同资源的重复引用。不能将外链仍原样保留的文章计为已完成图片托管。
- 保留已有文章路径、中文及数字 Slug、尾斜线行为与旧媒体别名。保留路径不意味着本次切换旧域名的 DNS 或提供旧域名重定向。
- 同 Slug、来源身份或媒体路径冲突不自动覆盖，必须列入冲突报告。资源缺失、无法解析的链接和不兼容内容先修复；不能修复的条目不发布。若现有导入器拒绝这些条目，应报告为未成功导入，不伪称已有完整工作稿。
- 原展示日期和更新时间不使用导入时间替代。UTC 展示保持一致。
- 沿用站名 `EZIOS`、副标题“技术笔记本”、作者 `Ezios`、中文简介及可支持的导航和社交信息；现有模型无法表达的信息列入差异报告。旧来源未发现头像配置，不凭空创建头像。
- 站点配置沿用当前 Comic 主题及可验证的主题版本，经现有配置修订和发布边界生效。Theme 仍只消费 Theme Model，不直接读取旧仓库或数据库。
- 新站公开地址使用独立博客入口，旧域名继续服务旧站。设置正确的站点地址并检查构建中的绝对链接。
- 使用隔离构建检查正式发布前页面。当前生产为 HTTP，内置私有预览要求同源 HTTPS；不降低认证预览的安全约束，不公开私有预览目录。
- 报告确认前不切换正式站点产物，包括站点配置的正式发布。必要的配置和文章检查在隔离环境进行。
- 正式发布必须经过作者对迁移报告的确认，只选择验收通过的原公开文章及明确确认的配置修订。其他已有工作稿和未公开配置不得顺带发布。
- 复用固定版本的发布任务、站点快照及发布产物切换能力；发布失败保留当前站点，不以复制文件绕过发布登记。
- 不预设新增 schema 或 API；必要兼容变更沿用既有契约。若实现需要新增契约，补充决策与对应验收。

## Testing Decisions

- 沿用已确认的验收范围：全量数据和资源核对，以及中文 Slug、表格、代码块和图片等代表页面检查。优先使用现有导入与发布集成契约作为一个主验收边界：固定源 → 预检 → 工作稿与修订 → 固定站点快照构建 → 静态 HTTP 访问。
- 好的检查验证作者和读者可观察的结果：预检无写入、内容保真、未公开内容不上线、重跑无重复、旧路径可访问、资源可读取、冲突不覆盖和失败保留原站点。不以内部函数调用次数或实现结构作为通过标准。
- 复用已有 Legacy Import 的 SQLite/PostgreSQL 夹具与真实来源集成检查，以及 Content/Publishing 的真实构建、静态资源和失败恢复检查；必要时在同一边界补充源草稿筛选和外链图片转换场景。
- 本次生产数据库验收使用 PostgreSQL；若修改共享导入或媒体能力，同时维护 SQLite 兼容性。真实源检查必须针对固定的新提交，不沿用旧提交的通过记录。
- 所有来源文章须在报告中获得明确结果：导入成功且待发布、未公开工作稿、冲突、未能导入或暂缓发布。分类统计应能与源清单逐项对账，不以总数相同代替内容正确。
- 核对每篇文章的标题、正文及必要转换差异、日期、Slug、分类、标签、封面和媒体映射。确认源公开状态与发布允许清单对应，未公开内容和问题文章不在清单中。
- 全量检查站内文章和媒体引用；验证下载后的外链图片内容有效、媒体映射正确、重复引用稳定及失败资源被报告。引用暂缓发布文章的链接也须纳入检查，避免通过文章上线后仍形成断链。
- 实际访问中文和数字文章路径、旧媒体路径、附件、首页、归档、分类及标签页面；代表页面验证 GFM 表格、围栏代码、语言标签、标题锚点和封面。构建成功不能代替渲染和 URL 编码检查。
- 在隔离环境核对备份恢复后的文章、媒体、配置和当前发布状态；验证失败或中断后保留当前站点，重复执行不会污染已有内容。
- 如使用 Playwright 或浏览器，复用本机已安装的 Playwright `1.63.0` 与 Chromium `153.0.8010.12`，不下载新版本。
- 实现变更后执行适用 Taskfile 检查；共享工程改动采用 `task check` 作为质量门禁，迁移行为还需专门的 PostgreSQL、真实来源和 HTTP 验收。报告记录执行版本、结果、证据及未执行检查的原因。
- 正式发布前提供迁移报告和隔离页面检查结果；作者确认后再发布。发布后补充生产 URL 和媒体访问结果，未执行项不标记通过。

## Out of Scope

- 切换旧域名、关闭旧博客、修改旧站 DNS 或建立旧域名重定向。
- 建立 GitHub 与 CMS 的持续内容同步或恢复 GitHub API 发布链路。
- 自动覆盖生产已有内容、自动发布所有工作稿或源草稿。
- 更换主题、重做旧主题布局或要求特殊组件像素级还原。
- HTTPS 改造、降低私有预览认证要求或公开私有预览目录。
- 新增搜索、评论、RSS、主题市场等与此次内容迁移无关的功能。
- 在本规格发布时执行生产导入、升级或正式发布。
