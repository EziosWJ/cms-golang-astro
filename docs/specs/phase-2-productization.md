# Phase 2：CMS 作者工作流产品化

状态：产品方向已确认，已发布 [Phase #20](https://github.com/EziosWJ/cms-golang-astro/issues/20)、[Spec #21](https://github.com/EziosWJ/cms-golang-astro/issues/21) 与 9 张 Tickets；作者工作流功能编码与本地检查已接入，真人独立试用待验收；见 [开发与验证记录](phase-2-validation.md)。

## 目标与用户

面向懂一点 Markdown、愿意自行部署的个人博主。首次接触产品的目标用户无需口头操作指导，应能完成写作、插图、预览、发布和再次修改，并区分保存、线上内容及失败恢复。

本阶段将现有 MVP 能力组织成日常作者工作流，不以本阶段完成宣称整个系统已生产就绪。单作者与权限边界沿用现有实现，不增加团队审稿流程。

## 已确认决策（Q1–Q22）

| 问题 | 决策 |
| --- | --- |
| Q1–Q3 | 个人 Markdown 博主；陌生目标用户独立完成流程；覆盖关键失败保护，完整生产运维另行规划 |
| Q4 | 登录默认进入文章列表；工作台保留为次级概览；系统入口收至下方 |
| Q5 | 标题和正文为主；默认源码，可切换正文预览或分屏；文章设置在可收起侧面板 |
| Q6、Q8 | 新旧文章均自动保存；标题或正文有非空内容，停止输入约 2 秒后首次创建；完全空白不创建 |
| Q9 | 当前输入保留，浏览器按账号与文章保存临时恢复副本；数据库仍是主数据源；提供恢复与清除 |
| Q10 | 冲突停止自动保存，比较本地与服务器内容，明确选择；不自动合并或静默覆盖 |
| Q7、Q11 | 网站预览可选；发布检查与简短确认；先保存并固定版本，保存失败不发布；期间可继续编辑 |
| Q12 | 重试原固定版本与发布最新修改分开，同站点串行保护继续生效 |
| Q13 | 网站预览按需更新；后续修改显示预览过期；正文即时预览随输入更新 |
| Q14 | 自动保存不逐次生成历史；“保存版本”和发布形成历史；时间、来源、比较、恢复只改工作稿 |
| Q15 | 媒体统一上传、缩略图、文件名搜索、进度与失败重试、插图/封面、引用与删除影响；保留附件 |
| Q16 | 编辑内快捷创建分类标签；设置显示未发布变更并独立发布，身份冻结规则保留 |
| Q17 | 轻量首次设置清单；允许先写文章；首次发布前补齐并发布必要站点配置 |
| Q18 | 默认未归档文章，草稿/已发布/有未发布修改筛选；归档次级视图；下线归档放更多操作 |
| Q19 | 桌面完整体验；平板正常写作；手机单栏完成编辑、上传、预览和发布，设置用抽屉 |
| Q20 | 工作台展示真实最近编辑、未发布修改、最近发布结果与写作/查看网站入口 |
| Q21 | 暂名“CMS 内容管理”，登录后显示站点名称；沿用克制蓝灰体系 |
| Q22 | 自动化、浏览器与关键故障验证，另由至少一位未参与开发的目标用户独立试用；真人未验收不标完成 |

## 交付与范围

具体行为及验收见 [作者工作流 Spec](phase-2-author-workflow.md)，实施依赖见 [本地 Tickets](../tickets/phase-2/README.md)。允许为真实业务反馈、筛选、引用查询和安全保存补充必要 API；本阶段不限定为 CSS 改动。

不纳入：完整所见即所得编辑器、团队审批、自动内容合并、图片裁剪压缩与目录系统、正式品牌设计、主题/导航编排、定时发布、永久删除、整站回滚、部分构建、完整部署升级/监控/备份恢复项目。

## 与既有设计的接续

保留 DB 主数据源、生成 Markdown 中间产物、内容身份与线上版本分离、发布串行/幂等、私有预览、媒体引用保护以及 Admin embed / Site 独立构建。浏览器副本仅是恢复保护，不参与发布选择，也不成为第二主数据源。

本阶段明确扩展 Phase 1 的“首版不提供版本差异比较”：新增只读比较，不改变不可变修订和恢复语义。新文章首次自动保存、浏览器恢复副本属于工作流扩展。“手动保存”改名“保存版本”，不是删除明确留存修订的能力。历史设计文档保留原阶段背景，以本阶段规格界定新增范围。

## 前阶段未完成项

Phase 1 已记录本地 task check、双数据库合约、浏览器及多窗口中断恢复验证，不能描述为完全未经验证。原有远端 CI、Windows/macOS 原生运行、旧站线上内容/URL/缓存/渲染、PostgreSQL 备份恢复、真实生产服务管理器/HTTPS/权限等待验收项继续追踪原记录。

这些事项不因 Phase 2 设计交付或本地体验验收而通过。实施前核实最新记录；若某项实际阻塞本阶段场景，记录阻塞与影响，不绕过保护或自动勾选。

## 完成标准

1. Spec 的正常、空态、错误、权限、恢复和响应式场景均有实际证据。
2. 桌面/平板/手机可完成核心任务，键盘可操作；现有设计体系与 Page Patterns 复用情况有记录。
3. 适用 Taskfile 检查通过，后端变更补齐双数据库合约；最终执行 task check。未执行项明确写明原因。
4. 至少一位符合画像、未参与开发的用户独立完成 Spec 中的真人任务；记录卡点、修复与必要复验。无人参加时保持待验收。
5. Tickets 区分编码、自动化验证、浏览器验证和真人验收，不以编码完成代替整体通过。
