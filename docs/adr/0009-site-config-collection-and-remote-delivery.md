# ADR-0009：站点配置集合与远端交付目标

状态：Accepted（2026-10-14，作者确认）

## 背景与谱系

本仓库曾存在一条已被放弃的远端发布方向，其决策记录为 ADR-0006（手动 Git 导出）、ADR-0007（单仓库 GitHub 发布）与 **ADR-0008（整站发布）**。三者只存在于未合并的 `old` 分支。

- 2026-10-13 15:04，`aaf9efd` 采纳 ADR-0008「本地与 GitHub 统一采用整站发布」，状态 Accepted。该 ADR 明文替代 ADR-0002 的单篇明确发布、ADR-0003 的逐篇目标与最新线上基线重试、ADR-0004 的部分构建提案，以及 ADR-0005 中「独立发布配置改变主题」的规则。
- 2026-10-13 15:34，`21c6e2f` 将 main 回滚到 pre-GitHub baseline。
- 2026-10-13 15:41–15:42，远端发布相关 issue #57–#78 全部以 `not_planned` 关闭。
- 2026-10-14，作者明确 **ADR-0008 为死决策**：该回滚废掉的是整条远端发布线，而不只是 GitHub 这一具体实现。

**结论：ADR-0006、ADR-0007、ADR-0008 均不生效。** 当前 main 的模型——ADR-0002 的工作稿/修订与逐篇发布、站点配置独立发布——是有效基线。本 ADR 不改变该模型，只在其上增加站点维度与一个远端交付目标。

本 ADR 编号取 **0009** 而非复用 0006：0006–0008 曾被真实采纳，ADR 编号是永久标识符，不复用。

## 决策一：站点配置成为集合，站点是呈现层

**站点配置（Site Config）**：一次对外交付所使用的呈现配置集合，包含主题与主题版本、站点名、描述、作者资料与公开地址（`publicUrl`）。**站点配置不拥有内容。**

`Site` 一词**保留**指 `CONTEXT.md` 中原有的含义（通过 Astro 生成的独立静态博客站点），不用来指代呈现配置；本文与 CONTEXT 中「站点」作为呈现配置的简写均不带 `Site` 标注。此约定见 `CONTEXT.md` 站点配置条目的 `_Avoid_`。

- 站点配置由单行单例改为集合。含 `role='local'` 的一条不可删除、可修改；本地链路（`deployment.Pointer`、`cms_publish_state.current_release_id`、媒体引用中的配置所有者）指向它。local 的特殊性来自**角色**，不是来自 id 或名字，因此它可改名、可改内容。
- 非 local 站点配置**每条站点一条修订链**；**保存即生效于下一次交付**，不产生发布任务，不参与「已上线配置」的推导。
- 已被交付记录引用过的站点配置**只能停用，不能删除**；停用可逆，删除不可逆。停用**不等于**下线线上站点——下线是独立的、需二次确认的动作。
- 站点需要**不可变标识符**，用于产物目录名与交付记录键，与可随时修改的站点名分离；改名不影响历史产物。

## 决策二：发布域保持单一

不向 `cms_publish_state`、`cms_publish_task`、`cms_release`、`deployment.Pointer`、`cms_published_article`、`slug_locked_at` 及产物保留策略引入站点维度。

- **内容权威恒为 local。** 任何非 local 站点的内容输入 = local 的当前线上版本。
- 因此非 local 站点在内容上**只能落后，不能领先或偏离**；「只把某篇文章发到远端站点」不被支持。漂移方向单一，因此「某站点落后本地多少次交付」是可计算、可显示的事实。
- 推论：远端交付的前置条件是 local 已有线上基线。local 从未发布过配置时，远端交付没有可用输入，必须明确失败并给出可操作提示。
- 本决策**排除**按站点选择内容（L2）与每站点独立发布状态（L3）。这两种模型要求为每站点维护独立的发布状态、基线、slug 锁定、首次发布时间与保留策略，属于发布域重写，不在本次范围。

## 决策三：远端交付目标（首版为 Cloudflare Pages）

**交付输入**：以 local 当前线上 release 的 manifest 为基线，替换**站点配置 `Config`** 与**本次交付的身份字段**（`AttemptID`、`ReleaseKey`），并固定 `PreviewTaskID` 不参与。后两项是让「同一 manifest 两次提交按内容哈希去重」与「待核实」可成立的前提；只替换 `Config` 会带着 local 那次尝试的身份。

- 交付**只依赖数据库中的 manifest 记录与受保护媒体**，不依赖 local 的产物文件；因此 local 的产物清理不影响远端交付。
- 字节必须**重新构建**：`publicUrl` 进入 canonical 与 `og:url`，产物与域名绑定，不能复用 local 已构建的文件；但**内容选择不重新推导**，否则同一站点的两个出口可能选出不同文章集合。

**产物根与私有预览边界（硬约束）**：`builder.Build` 目前只按 `PreviewTaskID` 在两个产物根之间选择（`releases/` 或 `previews/`，见 `cms-api/internal/builder/builder.go`）。交付必须使用**独立的第三个产物根**（`deployments/<site>/<key>/`），且**交付构建不得设置 `PreviewTaskID`**。

> **私有预览产物永不出境。** `previews/` 产物根由认证的私有 Astro 预览使用（经 `CMS_BASE_PATH=/api/v1/previews/{id}/`、由 Go 侧鉴权后服务，见 ADR-0004）。交付适配器**不得**以 `previews/` 或 `releases/` 作为上传源；只有交付自身生成的产物根可上传。实现者若按「目标」分支而漏掉这一条，私有预览会被推到公网。

**触发与串行**：手动触发；不排队、不自动、不由内容发布连带触发。交付**抢 local runtime root 的锁**，因此同一时刻只有一个 Astro 构建。

- 交付**不得进入 `Worker.Run` 的持有链**：单行 `blocked_reason` 一旦被写成非空，本地发布与远端交付会互相卡死。远端不可达或结果未知**绝不阻塞本地编辑与本地发布**。
- 同一站点不允许并发交付；已有在途交付时明确拒绝并提示等待。

**两阶段**：先以非生产分支创建部署得到**预部署（staging）**地址，对其做真实 HTTP 冒烟，再以生产分支提交**同一份 manifest**（按内容哈希去重，不重传文件）。成功边界是「生产部署生效」；仅构建成功或仅提交成功不记为交付成功。

**命名约定**：本文的「预部署」专指远端交付的第一阶段。仓库中的「**预览**」始终指认证的**私有 Astro 预览**，两者不是同一件事，**不得共用同一个词**——它们的产物根、认证方式与资源地址完全不同。

**记录与产物**：新建 `cms_site_deployment` 表与 `<RuntimeRoot>/deployments/<site>/<key>/` 目录，**不写入** `cms_publish_task` / `cms_release` / `cms_publish_state`。因此不触碰 `cms_publish_task.kind` 的 CHECK 约束，也不需要改动任何已应用的迁移。保留策略独立：最近 3 次成功交付 + 当前线上所用的一份；产物清理**必须显式跳过**该目录树，且不得把该表记录标记为已清理。

**失败语义**：

- 预部署通过而生产提交失败 → 记为**部分成功**（线上仍为上一版，内容已在预部署验证）；重试**固定原内容快照**，不重新取 local 基线。
- 结果不可知（超时）→ 记为**待核实**，通过查询该站点当前生产部署核实；不一致时阻塞**该站点**的后续交付，不自动重试。
- 进程被杀导致在途交付 → 重启**不自动重发**，记为需显式重试。
- **不提供取消**：远端一旦接受提交即无法撤回。

**上传单元**：产物目录本身，逐文件上传。**点号开头的路径一律排除**（当前命中 `.release.json`，本地服务本就拒绝供应它，但远端不会）；`_headers` 不是点号文件，必须上传。**不做 zip 归档**——逐文件上传是远端唯一入口，且 zip 与产物目录内容重复。

**呈现差异**：`_headers` **只在远端目标下生成**，local 产物保持逐字节不变；显式缓存分级（带内容哈希的资源可不可变长缓存，`index.html` 与站点 feed 不可）。单文件大小与文件数上限的检查在**构建前**执行并给出明确错误，而不是上传到一半失败。404 与 trailing slash 的语义需要**先实测再写代码**，不得假设与本地一致。

**Cloudflare 侧前置**：Pages 项目（含生产分支设置）由作者或部署脚本预先创建；CMS **不创建项目、不修改项目设置、不绑定自定义域名**。选定 Direct Upload 后不能改回 Git integration，这是一次性决定。因此站点配置中的 `publicUrl` 是**声明**而非配置动作。

**分支名从何而来**：两阶段提交需要 CMS 知道**生产分支名**（用于 `branch=` 命中 production）。该值随站点配置保存（非凭据，字段如 `productionBranch`），缺失时交付明确失败。**预部署分支名在代码中固定**，不暴露给作者配置。

## 决策四：远端凭据入库，但独立于站点配置数据

- 凭据存放于独立表 `cms_site_credential`，**不放入站点配置的 `Data`**。理由：`Data` 会进入不可变的配置修订链（该表带 `BEFORE UPDATE OR DELETE` 触发器，写入后**永久不可删**）、会写进构建工作区的 `manifest.json` 并交给 Astro 子进程、会落进 `cms_release.manifest` 与 `cms_publish_attempt.manifest` 列、并参与 `ManifestHash`。凭据一旦进入该路径，轮换后旧值无法清除。
- **读路径必须掩码**：配置读取接口绝不返回凭据，只返回「已配置 / 未配置 + 更新时间」。
- 凭据变更写审计。现有审计只记录模块、动作与请求元信息，不记录载荷，因此不构成泄漏路径。
- 不做静态加密：密钥与数据库同机，收益有限，却引入「密钥丢失即凭据不可恢复」。
- 数据库备份从此按密钥对待。

**偏离说明**：本项目既有惯例是凭据走 `configs/config.yaml` 与 `APP_` 环境变量（见 `cms-api/internal/config/config.go` 顶部说明）。本决策改为入库，理由是远端凭据需要作者在管理后台内配置与轮换，且数据库不进入 Git。ADR-0001 §22 约束的是凭据**不进入 Git**，不是不得进入数据库；该条依然完全有效。

## 决策五：分期

- **一期**：站点配置集合（迁移 + siteconfig 域 + 管理后台站点维度 + 把 local 的既有语义固定为角色）。**发布域不变。**
- **二期**：远端交付目标。

分期理由是避免在同一次变更中同时改动领域模型与接入外部依赖：一期出错是模型问题，二期出错是集成问题，可分别定位与验收。

**二期需要改动的既有共享代码（共两处，点名以防漏改）**：

1. `builder.Build` 的产物根选择（`cms-api/internal/builder/builder.go`）——当前只按 `PreviewTaskID` 在 `releases/` 与 `previews/` 之间选择，二期须增加交付的第三个根。**local 与预览两条既有路径的产物必须逐字节不变**。
2. `siteconfig.Read` 中推导「已上线配置」的 JOIN（`cms-api/internal/siteconfig/siteconfig.go`，`Joins("JOIN cms_publish_state s ON s.current_release_id=r.id")`）——这是单站点假设最硬的一处，须改为**只服务 `role='local'`**，非 local 站点不参与该推导。

其余改动均为新增（新表、新目录、新交付路径），不改动发布域既有逻辑。

## 明确不做

- 不实现按站点选择内容（L2）与每站点独立发布状态（L3）。
- 不做部分构建复用；每次交付都是完整重建与完整产物。
- 不由内容发布自动触发远端交付。
- 不保留交付归档 zip。
- 不在本次为 `deployment.Switch` 补审计事件、不为 publishing 增加 Prometheus 指标（均为既有缺口，另立 ticket）。

## 与 ADR-0001 的关系

- **§7（Git 边界）继续完全有效，且本 ADR 不恢复被废弃的链路。** ADR-0001 §7 废弃的是 `CMS → GitHub API → Markdown → Git Commit → Pages Build`，并规定 Git 不负责文章发布、文章数据库、附件、运行时构建产物与 CMS 状态。本 ADR 的远端交付**不使用 Git**：交付输入直接由 CMS 数据库生成并提交给远端平台的部署接口，Git 只承载源码。**这一点必须写明**，因为本仓库此前三次远端发布尝试都在不同程度上违反了 §7（把发布输入推入 Git 仓库、由 CI 构建、再回导制品），这正是该方向反复失败的原因；否则后来读者会以为被废止的链路又回来了。
- **§6（内容数据边界）继续有效**：CMS 数据库仍是内容主数据源；远端交付消费的是数据库派生的发布输入，该输入不反向成为编辑数据源。
- **§8（Runtime 目录布局）在二期扩展一层**：远端交付的产物与生成工作区置于 `<RuntimeRoot>/deployments/<site>/<key>/` 及对应生成目录之下；生产运行数据仍位于仓库之外。
- **§22（公开仓库）继续完全有效**：仓库为 Public，因此凭据与媒体永不进入 Git。决策四允许凭据进入数据库，与该条不冲突——受约束的是 Git，不是数据库。

## 替代范围

- 本 ADR **修订 ADR-0003 中「暂不接入远端部署平台」的边界**。ADR-0003 当初以「减少凭据、传输及远端切换依赖」为由排除远端平台；本决策已知情地改变该边界，缓解方式是：远端交付为手动拉取式触发、local 仍是内容权威、不随本地构建自动发生、远端不可用时不阻塞本地编辑与发布。
- ADR-0003 的其余部分——完整产物、只有线上版本切换成功才算发布成功、失败保留原站点——**继续有效**，并适用于远端交付。
- ADR-0006、ADR-0007、ADR-0008 **不生效**（见背景与谱系）。
- ADR-0002、ADR-0004、ADR-0005 不受影响；ADR-0001 见上节。
